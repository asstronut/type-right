# Changing text in a Rich editor from outside

Research for [#53](https://github.com/asstronut/type-right/issues/53) (map [#50](https://github.com/asstronut/type-right/issues/50)). Question: how can Type Right's content script replace the text of one Slip in a **Rich editor** so that the editor's own model accepts it and undo still works? Baseline: current stable Chrome and Edge (October 2026).

Researched 2026-10-17 by reading the current source of each library, Blink, and the specs. **Nothing here was tested live.** Every cell in the matrix comes from reading code, and the timing-sensitive cells are marked as such. Proving them is the job of [#58](https://github.com/asstronut/type-right/issues/58) and a verify run.

Confidence levels:

- **High**: read directly in current source or a spec, and backed up by an issue tracker or a second source.
- **Medium**: read in source, but the result depends on runtime details such as selection-sync timing, which nobody has tested.
- **Low**: inferred, or the product is closed-source.

## Answer in brief

1. **No library in scope checks `isTrusted`.** I grepped ProseMirror, Slate, Lexical, Quill, Draft.js and React's event plugin, and none of them read it. So the isolated-world origin of Type Right's events (`isTrusted === false`) is not a problem in itself. The one exception was short-lived: slate-react **0.128.0–0.132.x** (October 7–9, 2026) ignored script-dispatched input, paste and drop events. 0.133.0 reverted that after Grammarly, Text Blaze, Harper and ProWritingAid all broke. (High)
2. **`document.execCommand('insertText')` fires `input` but never `beforeinput` in Chrome.** Blink sends `beforeinput` only for commands from a menu or key binding (`EditorCommandSource::kMenuOrKeyBinding`), and `document.execCommand` uses `kDom`. Editors that work only from `beforeinput` (Slate) never see the edit. Editors that read the DOM after it changes (ProseMirror, Quill, Lexical, Draft.js, Gmail-style plain contenteditable) do. (High)
3. **A synthetic `beforeinput` has no default action.** The browser changes nothing; only an editor that handles the event itself (Slate, Lexical, Quill 2) acts on it. Since 2026-10-15 the Input Events spec explicitly tells editors to handle synthetic `beforeinput` from extensions (`insertReplacementText`, `insertFromPaste`, deletions) and prefers it over a synthetic `paste`. Chrome already accepts `targetRanges` and `dataTransfer` in `InputEventInit`. (High)
4. **A synthetic `paste` also has no default action.** It works only where the editor reads `clipboardData` and inserts the text itself. On **Quill 1.x** it is destructive: Quill 1 relies on the native paste landing in a hidden container, so a synthetic paste deletes the selected Slip and inserts nothing. (High from source; not tested live)
5. **Direct DOM mutation** is picked up by editors that watch DOM mutations (ProseMirror, Quill, Lexical for text-node edits only). Slate ignores it on desktop. Plain contenteditable accepts it, but the browser's undo stack loses the change. (Medium–High)

**Recommendation.** Apply in a Rich editor works in two steps:

1. Dispatch a synthetic `beforeinput` with `insertReplacementText`.
2. If no editor claimed it, fall back to `execCommand('insertText')`, except in Slate, where Apply should be hidden instead.

This is what the spec now recommends, and it is close to what Harper (open source) does. Details are under [Recommendation](#recommendation).

## The isolated world

- Content scripts share the page's DOM but not its JavaScript objects ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)). An event dispatched on a DOM node from the isolated world runs the page's listeners as usual. Platform objects passed in the event init (`DataTransfer`, `StaticRange`) are the same underlying objects, re-wrapped for the page's world. Expando properties set in the isolated world are not visible to the page. (High for the shared DOM; Medium for the wrapper detail, which comes from Blink's binding model rather than one cited line.)
- **`isTrusted` is `false`** on every event a script constructs, in any world. As point 1 above says, no editor in scope checks it. Slate's brief check (slate-react 0.128.0, [#6117](https://github.com/ianstormtaylor/slate/pull/6117)) was reverted in 0.133.0 ([#6198](https://github.com/ianstormtaylor/slate/pull/6198), with a Playwright regression test in [#6199](https://github.com/ianstormtaylor/slate/pull/6199)), because it "breaks multiple popular Chrome extensions" ([#6197](https://github.com/ianstormtaylor/slate/issues/6197)). The motivating issue ([#6116](https://github.com/ianstormtaylor/slate/issues/6116)) shows that some editor maintainers see script-injected input as a bug. **Risk: an editor could start checking `isTrusted` again.** Apply must detect when its edit was refused rather than assume success. (High)
- Events the browser fires *because of* `execCommand` (`input`, `selectionchange`) are dispatched by the user agent. Blink's internal dispatch marks them trusted (Medium; not traced to a single line). That makes execCommand robust even against a hypothetical `isTrusted` check.
- `document.execCommand` from a content script acts on the shared document and its selection. Type Right's textarea Apply already relies on this ([`entrypoints/content/hover.ts`](../entrypoints/content/hover.ts)). (High)
- Running in the page's main world (`world: "MAIN"`) would give access to editor instances: Lexical sets `rootElement.__lexicalEditor`, and TipTap sets `dom.editor` (found by code search in those repos). That is an adapter-level escape hatch, tied to library internals and to the page's CSP. It is not a general path. (Medium)

## Per-library evidence

### Blink: `execCommand`, `beforeinput`, undo

- `Document::execCommand` builds the command with `EditorCommandSource::kDom` ([document_exec_command.cc](https://github.com/chromium/chromium/blob/32c243c749d3a92483c15dc21398186fa1784bd5/third_party/blink/renderer/core/editing/commands/document_exec_command.cc), `GetCommand`). `EditorCommand::Execute` dispatches `beforeinput` only `if (source_ == EditorCommandSource::kMenuOrKeyBinding)` ([editor_command.cc](https://github.com/chromium/chromium/blob/32c243c749d3a92483c15dc21398186fa1784bd5/third_party/blink/renderer/core/editing/commands/editor_command.cc), `EditorCommand::Execute`). **execCommand never fires `beforeinput` in Chrome.** (High)
- After the edit, `CompositeEditCommand::AppliedEditing` dispatches `input` (with `inputType` and data) and registers an `UndoStep` on the frame's undo stack ([composite_edit_command.cc](https://github.com/chromium/chromium/blob/32c243c749d3a92483c15dc21398186fa1784bd5/third_party/blink/renderer/core/editing/commands/composite_edit_command.cc), `AppliedEditing`). Script DOM mutations don't go through this path, so they never become undo steps. (High)
- `TypingCommand::InsertText` reuses an open typing command if one exists. But `DOMSelection::UpdateFrameSelection`, which every Selection-API change goes through, sets `SetShouldCloseTyping(true)` ([dom_selection.cc](https://github.com/chromium/chromium/blob/32c243c749d3a92483c15dc21398186fa1784bd5/third_party/blink/renderer/core/editing/dom_selection.cc)). Selecting the Slip with the Selection API therefore makes the replacement its own native undo step. (High)
- `textInput` is dispatched only on composition confirm (`TypingCommand::InsertText`, `kTextCompositionConfirm`), so execCommand does not fire React's `onBeforeInput`. (Medium–High)
- `InputEventInit` includes `dataTransfer` and `targetRanges` ([input_event_init.idl](https://github.com/chromium/chromium/blob/32c243c749d3a92483c15dc21398186fa1784bd5/third_party/blink/renderer/core/events/input_event_init.idl)), and the constructor copies `targetRanges` into the event ([input_event.cc](https://github.com/chromium/chromium/blob/32c243c749d3a92483c15dc21398186fa1784bd5/third_party/blink/renderer/core/events/input_event.cc)). `ClipboardEventInit` has `clipboardData`, and `DataTransfer` has a public constructor. (High)
- When an EditContext is active, `EditorCommand::Execute` returns early for several commands. EditContext-based editors are outside this matrix, and the spec note below asks them to handle synthetic `beforeinput` too. (Medium)
- MDN: execCommand is deprecated, but "unlike direct DOM manipulation, modifications performed by `execCommand()` preserve the undo buffer" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Document/execCommand)). (High)

### Specs

- **Input Events Level 2** (editor's draft): a note under `beforeinput` says "Third-party browser extensions, such as spelling or grammar checkers, may modify the contents of editable elements by dispatching synthetic beforeinput events". It asks editors to treat synthetic `insertReplacementText`, `insertFromPaste` and deletion events like trusted ones, EditContext editors included. It prefers `insertFromPaste` over a synthetic `paste`, because `paste` carries no target ranges ([spec](https://w3c.github.io/input-events/), added by [w3c/input-events#185](https://github.com/w3c/input-events/pull/185), merged 2026-10-15; script-set target ranges by [#183](https://github.com/w3c/input-events/pull/183)). Untrusted events keep whatever target ranges the script gave them, or none. (High that the note exists; it is new, so editor adoption beyond the libraries below is unknown.)
- **Clipboard API**: a synthetic paste "can be manually constructed and dispatched, but it will not affect the contents of the document" ([spec](https://w3c.github.io/clipboard-apis/) §5.2.4). (High)

### ProseMirror / TipTap

Source: prosemirror-view @ [`ca4c78e`](https://github.com/ProseMirror/prosemirror-view/tree/ca4c78e9b56f1b164c0b3758b59d8748f11b7534) and prosemirror-history @ [`445409b`](https://github.com/ProseMirror/prosemirror-history/tree/445409bc99c88550c2312f5610829ecb25105a5f).

- ProseMirror is DOM-driven. `DOMObserver` runs a MutationObserver over `characterData`, `childList` and `subtree` ([domobserver.ts L53](https://github.com/ProseMirror/prosemirror-view/blob/ca4c78e9b56f1b164c0b3758b59d8748f11b7534/src/domobserver.ts#L53)). `readDOMChange` parses the changed range and dispatches `tr.insertText` or a replace step, through the `handleTextInput` prop, which is where TipTap's input rules hook in ([domchange.ts L265-L270](https://github.com/ProseMirror/prosemirror-view/blob/ca4c78e9b56f1b164c0b3758b59d8748f11b7534/src/domchange.ts#L265-L270)). The diff is computed against the document, not ProseMirror's selection, so execCommand doesn't depend on selection-sync timing. (High)
- The only `beforeinput` handling is a Chrome Android backspace hack, under the comment "support is so spotty that I'm still waiting to see where they are going" ([input.ts L806-L829](https://github.com/ProseMirror/prosemirror-view/blob/ca4c78e9b56f1b164c0b3758b59d8748f11b7534/src/input.ts#L806-L829)). Slate #6116 also states that "ProseMirror ignores the same event". (High)
- Paste: `editHandlers.paste` reads `event.clipboardData`, then `doPaste` → `replaceSelection` → `setMeta("uiEvent","paste")` ([input.ts L634-L667](https://github.com/ProseMirror/prosemirror-view/blob/ca4c78e9b56f1b164c0b3758b59d8748f11b7534/src/input.ts#L634-L667)). It uses `view.state.selection`, which syncs from the DOM on the asynchronous `selectionchange` event ([domobserver.ts L120-L132](https://github.com/ProseMirror/prosemirror-view/blob/ca4c78e9b56f1b164c0b3758b59d8748f11b7534/src/domobserver.ts#L120-L132)). So wait for `selectionchange` before dispatching. (Medium)
- History starts a new group when more than `newGroupDelay` (500 ms) has passed or the change isn't adjacent ([history.ts L277-L286](https://github.com/ProseMirror/prosemirror-history/blob/445409bc99c88550c2312f5610829ecb25105a5f/src/history.ts#L277-L286)). It also handles `beforeinput` `historyUndo` and `historyRedo` ([L411-L413](https://github.com/ProseMirror/prosemirror-history/blob/445409bc99c88550c2312f5610829ecb25105a5f/src/history.ts#L411-L413)). The browser-stack entry that execCommand also leaves behind is never used, because PM handles undo itself. (High)

### Slate

Source: slate @ [`ec41dac`](https://github.com/ianstormtaylor/slate/tree/ec41dac2567d2e4a441844f0b16f87f8a22b5a67), `packages/slate-react/src/components/editable.tsx`.

(High)
- It selects `getTargetRanges()[0]` when present ([L833-L853](https://github.com/ianstormtaylor/slate/blob/ec41dac2567d2e4a441844f0b16f87f8a22b5a67/packages/slate-react/src/components/editable.tsx#L833-L853)), calls `preventDefault()` for anything that isn't a "native" single-character insert ([L874-L877](https://github.com/ianstormtaylor/slate/blob/ec41dac2567d2e4a441844f0b16f87f8a22b5a67/packages/slate-react/src/components/editable.tsx#L874-L877)), and then for `insertReplacementText`, `insertText` and `insertFromPaste` calls `ReactEditor.insertData` (when `data` is a DataTransfer, checked by constructor name) or `Editor.insertText` ([L958-L1003](https://github.com/ianstormtaylor/slate/blob/ec41dac2567d2e4a441844f0b16f87f8a22b5a67/packages/slate-react/src/components/editable.tsx#L958-L1003)). (High)
- `onPaste` inserts only on browsers without `beforeinput`, for plain-text-only pastes, or on WebKit ([L2386-L2414](https://github.com/ianstormtaylor/slate/blob/ec41dac2567d2e4a441844f0b16f87f8a22b5a67/packages/slate-react/src/components/editable.tsx#L2386-L2414)). `isPlainTextOnlyPaste` means `types.length === 1` with non-empty `text/plain` ([slate-dom utils/dom.ts L93-L99](https://github.com/ianstormtaylor/slate/blob/ec41dac2567d2e4a441844f0b16f87f8a22b5a67/packages/slate-dom/src/utils/dom.ts#L93-L99)). (High)
- `RestoreDOM`, the MutationObserver, is used only when `IS_ANDROID` ([restore-dom.tsx L82](https://github.com/ianstormtaylor/slate/blob/ec41dac2567d2e4a441844f0b16f87f8a22b5a67/packages/slate-react/src/components/restore-dom/restore-dom.tsx#L82)). On desktop, nothing reads a DOM change that arrives without a `beforeinput`. (High)
- Undo: slate-history starts a new batch when a `remove_text` follows the user's `insert_text`, and merges the rest of the same flush into it ([with-history.ts L70-L110](https://github.com/ianstormtaylor/slate/blob/ec41dac2567d2e4a441844f0b16f87f8a22b5a67/packages/slate-history/src/with-history.ts#L70-L110)). One Apply is one undo step. (Medium–High)
- Applying while the editor isn't focused inserted text at the wrong place in Chrome ([slate#4801](https://github.com/ianstormtaylor/slate/issues/4801)). Focus the editor first. (Medium)

### Lexical

For every non-`insertText` type it calls `preventDefault()`, and for `insertReplacementText` it dispatches `CONTROLLED_TEXT_INSERTION_COMMAND` ([LexicalEvents.ts L1466-L1490](https://github.com/facebook/lexical/blob/cb21da40de69c1eedc2b9ec60001fef0d3b1770a/packages/lexical/src/LexicalEvents.ts#L1466-L1490)). - On `input`, Lexical uses its *previous* selection, not the DOM's. `$shouldPreventDefaultAndInsertText` names the execCommand case outright: "this is likely a dangling `input` event caused by execCommand('insertText')" ([LexicalEvents.ts L247-L254](https://github.com/facebook/lexical/blob/cb21da40de69c1eedc2b9ec60001fef0d3b1770a/packages/lexical/src/LexicalEvents.ts#L247-L254)). (High)

### Draft.js (archived)

Source: draft-js @ [`afdb5c3`](https://github.com/facebookarchive/draft-js/tree/afdb5c3177c13fd26cb0abbdc439488f3e21b73b) and React @ [`098d2e8`](https://github.com/facebook/react/tree/098d2e87a1f7142947418d15f63f975b58c4685b).

### React-controlled contenteditable

`react-contenteditable` emits changes from `onInput`, `onBlur`, `onKeyUp` and `onKeyDown` by reading `innerHTML`. It rewrites `innerHTML` only when the prop differs from the DOM ([react-contenteditable.tsx L48-L101](https://github.com/lovasoa/react-contenteditable/blob/ec221521e0da0d6d96ea32e6b8ed54666957824a/src/react-contenteditable.tsx#L48-L101)). execCommand therefore keeps both the app state and native undo in step. Hand-rolled React editors vary. (Medium)

## How other extensions apply suggestions

- **Grammarly** (closed source): dispatches synthetic `beforeinput` after setting the DOM selection. Evidence: Slate's source comment, Grammarly breaking when Slate ignored untrusted `beforeinput`, paste and drop events ([slate#6197](https://github.com/ianstormtaylor/slate/issues/6197)), and the spec note. Which `inputType` it uses, and what it does in ProseMirror or Draft (which ignore `beforeinput`), is not public. Long-running Grammarly bugs exist in Lexical ([#3428](https://github.com/facebook/lexical/issues/3428), [#5085](https://github.com/facebook/lexical/issues/5085)) and Slate ([#4801](https://github.com/ianstormtaylor/slate/issues/4801)). (Medium for the `beforeinput` claim; Low for everything else.)
- **Harper** (Automattic, open source, also broken by Slate 0.128) picks a strategy per editor ([computeLintBoxes/index.ts L120-L343](https://github.com/Automattic/harper/blob/64f35cd08743e40d91b7ef66f577ea95365b8834/packages/lint-framework/src/lint/computeLintBoxes/index.ts#L120-L343)). (High; read in source)
  - textarea: `execCommand('insertText')`.
  - **Slate and CKEditor**: synthetic `beforeinput` `insertReplacementText` with `targetRanges: [new StaticRange(range)]`. If the editor doesn't call `preventDefault`, it edits the text node directly and sends a synthetic `input`.
  - **Lexical**: edits the text node directly, then sends a synthetic `input`.
  - **Draft**: synthetic `beforeinput` `insertText` in a `setTimeout(0)`; if unhandled, it edits the DOM and sends a synthetic `input` with `inputType: 'insertText'`.
  - **Everything else** (ProseMirror, Quill, plain contenteditable): selects the range, edits the text node, sends a synthetic `input`. In Gmail-style editors this gives up native undo.
- **LanguageTool**: the current extension is closed source. The archived open add-on ("OUTDATED", last pushed 2023) applied fixes in contenteditable like this (Medium for the archived add-on; unknown for today's product):
  1. Collapse the selection into the target text node and send synthetic `mousedown` and `mouseup`.
  2. After 25 ms, set `textNode.textContent`.
  3. Send synthetic `input` and `change` events.

  Source: [contentscript.js L244-L328](https://github.com/languagetool-org/languagetool-browser-addon/blob/c3b19196aa299c335bdf88074087ae833b5f5977/webextension/cs/contentscript.js#L244-L328).
- **Text Blaze** and **ProWritingAid** also depend on synthetic events, per slate#6197. (Medium)

## Recommendation

For [#58](https://github.com/asstronut/type-right/issues/58) to decide. Apply in a Rich editor:

1. **Keep focus and selection in the editor.** The Hover card's Apply button should `preventDefault()` on `mousedown`, as editor toolbars do, so the click doesn't move focus. Then focus the editable root.
2. **Select the Slip with a DOM `Range`** (the Selection API, which also closes Chrome's open typing command). **Wait one task for `selectionchange`**, so that ProseMirror, Lexical and Draft sync their own selection first.
3. **Dispatch `new InputEvent('beforeinput', { inputType: 'insertReplacementText', data, dataTransfer, targetRanges: [new StaticRange(range)], bubbles: true, cancelable: true })`** on the editable root. `dataTransfer` holds `text/plain` only. Slate ≥ 0.133, Lexical and Quill 2 apply it and call `preventDefault()`. ProseMirror, Draft, Quill 1, plain and React-controlled contenteditable ignore it and leave the DOM alone, since an untrusted event has no default action. Slate reads `dataTransfer` before `data`; Quill reads `data` first.
4. **If `defaultPrevented` is false and the Slip's text is still in place, call `document.execCommand('insertText', false, suggestion)`.** ProseMirror, Quill 1/2, Lexical, Draft and plain or React contenteditable all take it, each with working undo (native undo in Gmail-style editors). **Never take this fallback in Slate** (`[data-slate-editor]`). There it would desync the model, so hide Apply instead. That covers slate-react 0.128–0.132, and any future `isTrusted` check.
5. **Check that it stuck.** After a frame, re-read the Field's text: the suggestion must be at the Slip's offsets, and the editor must not have reverted it. If not, treat the editor as refusing programmatic edits and hide Apply there. The map already allows this. How to check is #58's question.

Avoid as general mechanisms:

- **Synthetic paste**: it deletes the Slip in Quill 1, depends on selection sync, and triggers paste-specific site handlers. The spec prefers `insertFromPaste` `beforeinput` anyway.
- **Direct DOM mutation**: Slate ignores it, Lexical reverts structural edits, it breaks native undo, and it has to be followed by synthetic events.

Keep both as per-site adapter options only if a site breaks both steps above.
