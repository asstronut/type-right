# Drawing underlines in a Rich editor without touching its DOM

Research for issue #52 (map #50). The question: in current stable Chrome and Edge, what is the best way to draw Slip underlines (wavy, one colour per Kind) over a Rich editor without changing the editor's DOM? The two candidates are (a) the CSS Custom Highlight API and (b) overlay elements positioned from `Range.getClientRects()`. The research also looks at how Grammarly and LanguageTool do it.

Confidence labels: **verified** = checked in a primary source and reproduced in Edge 155. **high** = primary source, not reproduced. **medium** = primary source is indirect (bug reports, source reading plus my inference). **low** = inference or unverified.

## Answer

Use the **CSS Custom Highlight API**. Register four named highlights, one per Kind. Fill them with `StaticRange`s rebuilt from the Field's text offsets after every edit or re-render. Hit-test hovers with `CSS.highlights.highlightsFromPoint()`. Everything below works from a content script's isolated world in Edge 155, and the editor's DOM is never touched. The browser paints the underline as part of the text, so scrolling, clipping, z-order, transforms and reflow need no code from us. Those are exactly the jobs that make overlays expensive and fragile; Grammarly's own write-up lists them as its hardest problems.

The approach has three costs. We must rebuild ranges ourselves, because live Ranges collapse or even grow when an editor rewrites text nodes. The hover target is the glyph box, so we have to probe a few pixels above the pointer to catch the underline. And the highlight registry is shared with the page, so the page can see or clear our highlights.

Bonus finding: `OpaqueRange` (`textarea.createValueRange(start, end)`) ships in Chrome 152 and works in Edge 155. It lets the same highlight path draw underlines in a `<textarea>`. That opens the way to **one rendering seam for both kinds of Field**, which bears on #50's "One Field interface" item.

## Evidence

### Experiment

`research/underline-rendering-probe/` holds a throwaway MV3 extension and a CDP driver (`node drive.mjs <path-to-msedge.exe>`). The extension's content script (isolated world, `manifest.json` `css` for the `::highlight()` rules) registers highlights on a local page with a plain contenteditable, a contenteditable inside an open shadow root, an inner scroller and a textarea. It then hit-tests, mutates the DOM the way editors do, rebuilds the ranges, scrolls, benchmarks, and lets the page call `CSS.highlights.clear()`. I ran it on **Edg/155.0.4283.60** (headless, Windows 11). Branded Chrome 137+ ignores `--load-extension`, so I did not run it in Chrome. Chrome and Edge share the Blink code involved, so I expect the same results (high).

| **Live `Range`s do not survive editor re-renders.** (1) Typing before the Slip in the same text node shifts the range correctly. ### OpaqueRange: the same path for textareas

| Claim | Source | Confidence |
|---|---|---|
| `OpaqueRange` ran as an origin trial in 148-150 and **ships in Chrome 152**. The blink-dev intent was delayed out of 149 by spec comments. It is at WHATWG Stage 2, Chromium-only for now, and the Microsoft Editor SDK team validated the design. | [chromestatus 6297362687066112](https://chromestatus.com/feature/6297362687066112) (API: origin trial 148-150, ship 152), [blink-dev intent](https://groups.google.com/a/chromium.org/g/blink-dev/c/otEJ9AacRg4) | high |
| In Edge 155, with no flags, `textarea.createValueRange(18, 25)` returned an `OpaqueRange`. Adding it to the spelling highlight **painted a wavy underline inside the textarea**. `getClientRects()` gave its box, and `highlightsFromPoint` hit it. After typing `Hi. ` at the start, the range followed to 22-29. | experiment + screenshot `edge-155-after-typing.png` | verified |

So textareas could drop the mirror div and share the Rich-editor path. Two caveats: the API is new and Chromium-only, so the mirror div is the lower-risk default until #50 decides the Field seam. And Chromium's highlight code still checks `RuntimeEnabledFeatures::OpaqueRangeEnabled`, so the feature flag still exists and could in principle be turned off remotely (low).

### (b) Overlays positioned from `Range.getClientRects()`

| Claim | Source | Confidence |
|---|---|---|
| This is what Grammarly does today, as of its 2022 write-up. Underlines are thin divs in one container appended as the last child of `<body>`, positioned from `Range.getClientRects()` relative to the field's `getBoundingClientRect()`. They are recalculated only when the text or the field's size changes; scroll moves only the container. | [Grammarly engineering, "Making Grammarly Feel Native On Every Website"](https://www.grammarly.com/blog/engineering/making-grammarly-feel-native-on-every-website/) (updated 7 Mar 2022) | high (as of 2022) |
| Grammarly lists the costs. No event reports an element's position, size or style changing, so it combines many signals (scroll, resize, mutations, stylesheet changes, input, IntersectionObserver) plus a roughly 1-second polling fallback, and alignment is "eventually" right. Polling layout reads at 60 fps used over 90% CPU on Facebook. `getClientRects()` forces reflow and makes scroll handlers janky. Clipping by nested overflow containers, sticky headers and popups covering the text (underlines drawn on top of a formatting popup) are open problems. | same | high |
| Measured here: `getClientRects()` costs about 0.007 ms per range when layout is clean. When layout is dirty, the first measurement pays for a forced layout: 1.3-3.1 ms for 200 ranges on a 4,000-word editor. The ranges are cheap; the forced layout and the follow-up work (scroll sync, clipping, z-order) are what cost. | experiment | verified (headless numbers, low as absolute values) |
| We would still need the same range-rebuild logic as in (a), because the ranges to measure come from text offsets either way. Overlays avoid none of (a)'s range problems; they only add positioning problems. | follows from the evidence above | high |

## Recommendation for the design (#57 prototype, #50 spec)

1. **Four highlights per window**, named with a unique prefix (e.g. `type-right-spelling`), with priorities ordered so that overlapping Slips stack predictably. Ship the `::highlight()` rules with the content script's CSS. Injecting a stylesheet is not a DOM change to the editor, and it reaches open shadow roots through inheritance.
2. **Rebuild, don't track.** After every text read (edit, IME commit, editor re-render), map each Slip's string offsets to DOM positions and replace the Field's ranges with fresh `StaticRange`s. Never rely on live Ranges following the text; they collapse or grow. To avoid one frame of wrong underlines after a re-render, rebuild in the MutationObserver callback (a microtask, before paint). The prototype should confirm this.
3. **Hover** = a passive `mousemove` listener on the editable root, then `highlightsFromPoint(x, y, {shadowRoots})`, with a second probe at `y - slop` for the underline area. Map `AbstractRange → Slip` with a `Map`.
4. **Guard the shared registry.** On each render, check that `CSS.highlights.get(name)` is still our object and re-set it if not. Pages that call `CSS.highlights.clear()` are rare but real.
5. **Textareas**: keep the mirror div for now. Evaluate moving them to `OpaqueRange` highlights in the Field-interface ticket, since that would make rendering and hover one code path.

### Main risks to test in the prototype (#57)

- Re-render timing: whether rebuilding in the MutationObserver callback avoids flicker in ProseMirror/Lexical-style editors, and the cost of offset→DOM mapping on long Gmail threads.
- Native spellcheck squiggles (painted above custom highlights) and Grammarly's underlines sitting at the same position as ours. A larger `text-underline-offset` may be needed.
- Hover slop size versus line spacing: probing upward must not catch a Slip on the line above.
- Editors in iframes (`allFrames`) and in closed shadow roots (`chrome.dom.openOrClosedShadowRoot`).
